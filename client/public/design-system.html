The HelloCircle Design System

A single, recognizable visual and behavioral language for a local participation product — audited from the real, running codebase, not designed from a blank page. Swiss structure carrying warm, human, local content.

167 files audited across consumer, booking, vendor, admin and auth surfaces 100+ files unified across 16 commits 0 raw-radius call sites remain — lint-tokens.mjs is clean 1 real cross-device save-sync bug found and fixed
01 — Overview

Executive summary

What this document is, what it found, and what it changed.

HelloCircle already had the bones of a real design system before this pass started — a CSS-variable token layer with light/dark themes, a space/type/radius scale, a shared ui.tsx primitive library, and even a token-regression linter (lint-tokens.mjs). What it didn't have was full adoption: dozens of pages still hand-rolled buttons, cards, and section headers instead of reaching for the shared ones, three different files disagreed about what color "full" should be, and the same join action read as three different verbs depending on which page you were standing on.

What this pass did

  • Built Five new shared primitives: ParticipantStack, AvailabilityBadge + availabilityFromSpots(), a generalized SectionHeader, a named zIndex scale, and a gameCta.ts module so the game-join verb can't diverge between the results list and the game's own detail page again.
  • Named Three real, repeated-but-unnamed color values as tokens: colors.textSoft (a genuine third body-text tier, not a duplicate — see §Color), photoOverlay (the gold/white hero-image badge treatment), and statTile (the admin/vendor KPI icon palette).
  • Fixed A real bug: ExperienceDetail.tsx rendered the identical "Full" state in two different colors depending on which part of the page you looked at.
  • Unified CTA language for Circle joining ("Join"/"Follow" → "Join Circle"), game joining (list and detail page now share one rule), and password-reset ("Update password" → "Set password").
  • Migrated CentreDetail, ClubDetail, BookingFlow, RegistrationFlow, ProgramDetail, and NotFound onto the shared Button/BackLink components, and added real map embeds where a listing has coordinates but the page only linked out to Google Maps.
  • Restructured ProgramDetail.tsx onto the main/rail detail pattern (it was the one page that abandoned it entirely), and added a mobile sticky CTA bar to CentreDetail/ClubDetail, whose entire price/CTA rail — button included — disappeared below the fold on mobile.
  • Adopted AuthShell for ForgotPassword, ResetPassword, and AcceptInvite — three vendor/admin auth-adjacent pages that were a second, undeclared "simple page" shell competing with the real one.
  • Unified the landing page's entire token system (client/src/landing/theme.ts) onto the shared brand colors and Bricolage Grotesque/Hanken Grotesk pairing — it ran on a separate green, a separate font pairing, and separate accent names, with a comment arguing that was deliberate. Every landing component kept working unchanged; only the token values moved.
  • Closed the entire raw-radius backlog — 194 call sites at audit time, mechanically swept to 0 across 65 non-landing files plus the 5 landing files, verified behavior-preserving (each replacement is an exact value match, so the rendered CSS is byte-identical).
All six roadmap phases in §Migration roadmap have real progress now — foundations, primitives, and every P0/P1 item from the original audit are done. What's left is P2/P3 polish: card image aspect ratios, and Home.tsx's own deliberate local button/chip system. See §Page consistency matrix for the current, honest state of every page.
02 — Overview

Visual audit

What already works, read straight from the code — three independent passes across consumer pages, booking/place pages, and nav/auth/vendor/admin/landing.

Keep — patterns already doing their job

  • The CSS-variable token layer (theme.ts → index.css) already carries full light/dark support to every one of its ~970 call sites with zero per-call-site changes — the right architecture, just not yet fully adopted.
  • Button, Card, EmptyState, Avatar, and Tabs are near-universal outside Home.tsx — most pages already reach for them instead of hand-rolling.
  • AuthShell genuinely unifies Login, SignIn, SignUp, and EmailLinkSignIn — same split-screen, same logo treatment, same heading scale.
  • NavSidebar + DashboardTopPanel give the Vendor and Admin dashboards real structural parity, not just a shared look.
  • The base participation-status wording ("Full" / "N spots left") had already propagated by habit to ~8 independently written call sites even before this pass named it as a real component.

Duplications found

  • Overlapping "who's going" avatars, hand-copied identically in two files merged into ParticipantStack.
  • The eyebrow + title + subtitle section header, hand-copied across Home.tsx and Circles.tsx with drifting sizes merged into SectionHeader.
  • A diagonal-stripe photo placeholder gradient, copy-pasted verbatim into 7+ card components open — a real candidate for a shared PhotoPlaceholder pattern.
  • Game participation-state logic (needs/available/full), independently reimplemented in the results list and the detail page's join card with two different rules merged into gameCta.ts.

Inconsistencies found

  • Six different verbs in play for "commit to this listing" across Games, Circles, Experiences, and Programs: Check availability, Register, Book, Enroll, Confirm, Join — no documented mapping of which object type gets which verb (see §Signature patterns for the standard this document sets going forward).
  • Three unrelated implementations of "spots left / full" status coloring in one file (ExperienceDetail.tsx) fixed.
  • An ungoverned mini-palette of purple/blue/gold hexes sitting next to proper colors.* tokens in the same admin stat row named as statTile.
  • The landing page (client/src/landing/) ran on an entirely separate token file — different green, different font pairing, different accent names — with no shared foundation at all fixed — now aliases the shared tokens.

04 — Overview

Brand & visual principles

Swiss editorial structure, carrying warm local-participation content.

Human, not corporate

Real activity photography, plain verbs, first names. Never "engagement," never "leverage."

Structure over decoration

Alignment, whitespace, and type hierarchy carry the design. Borders and dividers before shadows and gradients.

Participation is the hero

Who's going, what's needed, what's next — the product's own data is the visual interest, not illustration.

HelloCircle should never read as Eventbrite, Meetup, Airbnb, or a generic Tailwind template — not through decoration (no gradients, no neon, no 3D illustration) but through product behavior: the eyebrow-header rhythm, the participant stack, the "I'm in" / "Start something" / "Add my interest" vocabulary, and the green-participation / orange-urgency color logic that recur identically everywhere they apply.

06 — Foundations

Typography

One display face, one body face, everywhere. No mixing beyond these two — this document's own token names use a monospace utility face, which is the one deliberate exception (code/token legibility, not brand voice).

Bricolage Grotesque

Display — headings, eyebrow labels, prices, stat values. Bold, slightly quirky, editorial.

Hanken Grotesk

Body — everything else. Clean, compact, highly legible at small UI sizes.

Type scale

hero / 38·800Find your people
section / 28·700What's happening next
card / 20·700Badminton — Tuesday 7:30pm
label / 15·600Group size
eyebrow / 11.5·700Upcoming

hero is for a page's own <h1> only. Everything one level below a page title uses section — this scale intentionally has four steps, not eight; HelloCircle doesn't run long-form article content that would justify a denser one.

07 — Foundations

Grid & layout

Disciplined, Swiss-influenced, with room for the landing page to run more expressive photography inside the same container width.

  • Max content width: 1440px, centered, 24px page gutters below 900px.
  • Detail pages: an 8-column-equivalent main content column against a 4-column-equivalent decision rail (1.6fr / 1fr in practice) — see §Detail page pattern.
  • Discovery grids: 3 or 4 cards per row on desktop, collapsing to a horizontal scroll or single column under 860px.
  • Breakpoints: mobile 640 · tablet 860 · tabletWide 900 · desktop 1024. One stray value (560px) exists in index.css with no corresponding token — tracked in §Deprecation.

09 — Foundations

Radius, border, shadow

A deliberately small radius system — every call site now uses the token, not a raw number.

control — 10px

Inputs, buttons

card — 16px

Cards, panels

pill — 999px

Badges, chips, avatars

Borders are the primary structuring tool: a subtle 1px border by default, borderStrong for interactive/selected states. Elevation stays restrained — most cards are border-only or border-plus-a-hairline-shadow; stronger elevation (shadow-lift) is reserved for menus, dialogs, and floating actions, never a resting card.

Governance: lint-tokens.mjs reported 194 raw borderRadius: 10 / 16 / 999 literals at audit time — swept to 0 across all 70 flagged files (65 app + 5 landing) in a single mechanical, behavior-preserving pass. The linter now passes clean; it stays in CI-equivalent use to catch new regressions.
10–11 — Foundations

Iconography & photography

Iconography

One hand-authored icon set (components/icons.tsx), consistent stroke weight throughout. Icons clarify, they don't decorate — location, calendar, people, duration, save, share. No icon-per-line-of-text.

18 — Patterns

Detail page pattern

Main column for understanding, right rail for the decision — the pattern is real on two of five detail pages and should extend to the rest.

Main — understanding

About, facilities/what's included, accessibility, location map, related programs/games.

Rail — decision

Price, availability, the one primary CTA, trust bullets. Sticky on desktop.

CentreDetail, ClubDetail, and now ProgramDetail fixed all implement this split — each gained a shared Card rail, shared Button, and a mobile sticky bar where the primary action would otherwise disappear. HostProfile and ProviderProfile stay single-column on purpose — they're profiles, not transactions, so there's no decision to put in a rail. 19 — Patterns

Empty, loading, error, success

Empty

Headline, one-line explanation, a primary action ("Add my interest", "Start something"). EmptyState is shared and now used by FreeTimeMode/MakeItHappen too fixed — both hand-rolled a dashed-border box before.

Loading

Shape-matched skeletons (CardSkeleton, ListingDetailSkeleton, RowSkeleton) — never a generic spinner for page content.

Error

Inline for forms, a banner for page-level failures. Direct language: "Connection failed. Please try again," never "Oops!"

Success

A toast for a small action; a contextual success state ("You're in! · Sat 09:00 · View plan") for a major one. No confetti by default.

Cards & Listings

Shared SaveButton — a real bug fix, not just dedup

Six independently hand-rolled heart buttons collapsed into one components/SaveButton.tsx — but the more important fix was behavioral, not visual.

Before this pass, DiscoverRow.tsx's card was the only one that synced a signed-in resident's save to the server. CentreCard, ClubCard, CirclePlanCard, Games.tsx's JoinGameCard, and ExperienceKindBrowse's browse card all wrote to localStorage only — a resident favouriting a centre from a discovery grid silently never reached their account or synced across devices, while the identical action from the homepage's "Happening today" row did. Every card now shares useSavedState(), the one correct implementation.

28 — Governance

Design QA checklist

  • ☐ Every button is <Button>/<LinkButton> or has a documented reason not to be
  • ☐ No new raw hex — reach for an existing colors.* token, or name a new one if the value is genuinely distinct and repeated
  • ☐ npm run lint:tokens --workspace client (via node scripts/lint-tokens.mjs) passes with no new failures

Final visual language definition

HelloCircle uses a warm Swiss-editorial design language built around real activity photography, structured typography, disciplined grids, compact participation metadata, green action states, restrained orange urgency, and people-centered language. Its interface prioritizes what people are doing next, who is joining, and how to participate, using generous whitespace and minimal decoration rather than traditional dashboard UI.

The test that matters: open five random HelloCircle screens, hide the logo. Do the buttons behave the same? Does "I'm in" mean what you'd guess? Are the status colors predictable? After this pass, the foundations and a first wave of pages pass that test. The rest is a tracked, prioritized, incremental migration — not a gap pretending to be finished.
